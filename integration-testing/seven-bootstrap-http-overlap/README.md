# Seven Bootstrap HTTP Overlap

Approximates the reported production failure where six bootstrap definitions
run normally, but adding a seventh leaves only lightweight heartbeat activity
while HTTP collection runs accumulate.

The test runs the same agent image twice:

1. with six independent bootstrap definitions;
2. with seven independent bootstrap definitions.

Each deployment has four timer-triggered steps:

- a scripted heartbeat;
- a successful HTTP collector;
- two overlapping HTTP collectors with a 60-second timeout;
- two overlapping HTTP collectors with a 120-second timeout.

The scenario-local HTTP server deliberately responds to the last two collectors
after their configured timeout. The slow steps do not use `singleThreaded`, so
successive timer invocations overlap as they would in the reported configs.
The test verifies that heartbeat and successful HTTP collection continue for
every deployment, records maximum slow-request concurrency, checks activation
logs, and verifies that the agent stops within a bounded interval.

The agent is configured with `OPSCOTCH_AGENT_METRIC_PROPERTIES`. A dedicated
NDJSON endpoint captures delivered internal agent metrics, and the runner also
parses generated internal metrics from `SendMetric` diagnostics. Each run
preserves:

- delivered internal metric captures for the six- and seven-deployment phases;
- locally generated metric captures parsed from `SendMetric` diagnostics;
- filtered diagnostic metric captures;
- workflow metric counts;
- fixture-server concurrency snapshots;
- agent logs.

Artifacts are written under `artifacts/<UTC timestamp>-<pid>/`. Override this
with `INTEGRATION_TEST_ARTIFACT_DIR`.

The summary distinguishes metrics generated by the registry from metrics
delivered to the NDJSON endpoint. Under severe scheduler starvation the
in-process buffered metric sender can also stall; in that case the filtered
diagnostic artifact falls back to locally logged generated metrics.

The default time scale is `0.1`: 60/120-second timeouts become 6/12 seconds and
a 10-second timer period becomes 1 second. This preserves the concurrency ratio
while keeping the test practical. The agent container defaults to one CPU,
512 MiB memory with no swap, and a 512-PID limit. Each phase runs for 75 seconds
so the default one-minute internal metric publication interval is observed.

Run:

```bash
OPSCOTCH_LEGAL_ACCEPTED=... ./runtest.sh
```

Use production timings:

```bash
SCENARIO_TIME_SCALE=1 \
INTEGRATION_TEST_PHASE_SECONDS=150 \
OPSCOTCH_LEGAL_ACCEPTED=... \
./runtest.sh
```

Stress controls:

```bash
SLOW_COLLECTORS_PER_TIMEOUT=6 \
OPSCOTCH_AGENT_CPUS=0.5 \
OPSCOTCH_AGENT_MEMORY=384m \
OPSCOTCH_AGENT_PIDS_LIMIT=384 \
./runtest.sh
```

Optional agent image:

```bash
OPSCOTCH_AGENT_IMAGE=ghcr.io/opscotch/opscotch-agent:3.1.6-dev ./runtest.sh
```

## Local JVM mode

Build the local agent, then run the same six- and seven-deployment phases
without Docker:

```bash
cd /home/jeremy/dev/opscotch/hopscotch
./mvnw -pl agent -am package -DskipTests

cd /home/jeremy/dev/opscotch/community/opscotch-community/integration-testing/seven-bootstrap-http-overlap
./run-local-java.sh
```

The local runner uses the Quarkus `local` profile, rewrites container fixture
and persistence paths, samples JVM thread counts, captures a thread dump, and
requires:

- heartbeat and fast-collector delivery at least 65% of configured timer
  opportunities for every deployment;
- internal agent metric generation during saturation;
- an observable timer admission rejection;
- no threads blocked in workflow permit admission;
- no more than 100 live JVM threads by default;
- graceful shutdown within 15 seconds with no active slow fixture requests.

The expected passing behavior depends on the agent default
`OPSCOTCH_TIMER_ACTIVE_MAX=2`, which leaves global workflow headroom for the
fast and heartbeat paths. Delivered internal agent metrics are recorded when
the existing in-process buffered metric sender drains; generated metric logs
remain the runner assertion until monitoring isolation is implemented. Raising
the per-timer limit can be useful for some workloads, but this scenario
intentionally catches values that allow the slow timers to consume all global
workflow capacity.

Relevant controls:

```bash
OPSCOTCH_AGENT_JAR=/path/to/quarkus-run.jar \
INTEGRATION_TEST_PHASES="6 7" \
INTEGRATION_TEST_OUTPUT_TOLERANCE_PERCENT=65 \
INTEGRATION_TEST_MAX_LIVE_THREADS=100 \
INTEGRATION_TEST_STOP_LIMIT_SECONDS=15 \
./run-local-java.sh
```
